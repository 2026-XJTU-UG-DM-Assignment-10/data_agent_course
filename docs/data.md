## 2. 字段含义

固定 17 列，顺序即 `src/schema.py` 的 `CSV_COLUMNS`：

- **14 个特征**：`age`、`workclass`、`fnlwgt`、`education`、`education_num`、`marital_status`、
  `occupation`、`relationship`、`race`、`sex`、`capital_gain`、`capital_loss`、`hours_per_week`、
  `native_country`。其中 6 个数值字段是 `age`、`fnlwgt`、`education_num`、`capital_gain`、
  `capital_loss`、`hours_per_week`，其余 8 个为类别字段。
- **`income`**：标签，只有 `<=50K` 与 `>50K` 两个合法值。
- **`_source_id`**：原始记录的稳定来源 ID，形如 `S025957`。复制行保留**相同** ID，因此这一列不要求逐行唯一；它用于追溯“这一行来自哪条原始记录”。
- **`_group_id`**：在注入问题**之前**按规范化后的 14 个特征计算的 SHA-256 前 16 位签名，形如 `G5f3a…`。划分按组进行，因此训练与测试的组集合不相交。

### 两个 ID 为什么不做特征

`_source_id` 与 `_group_id` 只承担**审计**和**防泄漏**职责，不携带关于收入的真实信息：

- 把 `_source_id` 当特征，模型等于在读“这是第几条记录”，训练集上能拟合噪声，换数据立刻失效。
- 把 `_group_id` 当特征更危险——它由特征本身算出，等于把特征信息重复喂一遍，还会让同组记录在划分时暴露自己属于哪一侧。
- 同理，标签 `income` 绝不能进特征。

分类器显式使用 `FEATURE_COLUMNS` 选择特征，禁止写成“除标签外的所有列”，就是让这条边界落在代码里而不是靠约定。

## 3. 抽样与分组划分

- 固定种子 `42`，从 32,561 条参考池无放回抽取 10,000 条。
- `_group_id` 用确定性序列化 + SHA-256，不用跨进程不稳定的 Python `hash()`。
- 按**整组**分配，目标训练占比 70%。同一 `_group_id` 只能落在一侧。

| 指标 | 实际值 |
| --- | --- |
| 参考记录 | 10,000 |
| 训练集 `train_reference.csv` | 7,000 |
| 测试集 `test_reference.csv` | 3,000 |
| 训练组数 | 6,997 |
| 测试组数 | 3,000 |
| 训练/测试组交集 | **0** |
| 训练集 `_source_id` 重复数 | 0 |

训练组数（6,997）比训练行数（7,000）少 3，正对应第 4 节说的 3 行原生完全重复：它们签名相同，被整体保留在同一侧。

### 为什么先划分再注入

顺序是 **抽样 → 分组 → 划分 → 只对训练侧注入**。原因有三个：

1. **避免泄漏**：若先注入再划分，同一个真实人的记录可能因注入差异被拆到两侧，测试集就“见过”训练集来源。
2. **测试集要保留真实分布的参照**：测试集不注入任何人为问题，代表“拿到一份未被人为加工的真实数据时，系统表现如何”。
3. **复制行归属可控**：复制发生在划分之后，副本天然继承来源行的 `_group_id` 与 `_source_id`，不可能跨集合。

防跨集合的具体做法：

- 划分单位是 `_group_id` 而非行，任何签名相同的记录（含原生重复和后来的复制行）只能出现在同一侧。
- 注入后**不重算** `_group_id`，按公共接口要求保留注入前的值；否则被改坏的记录会算出新签名，可能绕过组约束。
- 复制行保留原 `_source_id`，“哪些行是副本”在审计时可查，但分类器看不到这两个字段。

### 4.3 最终检测统计（`train_dirty.csv`，7,140 行）

`profile_data(dirty, dataset="train", stage="before")` 的实际输出：

| 指标 | 值 | 计数单位 | 与注入的关系 |
| --- | --- | --- | --- |
| `row_count` | 7,140 | 行 | 7,000 + 140 复制 |
| `missing_by_column` 合计 | **5,815** | 单元格 | 原生 853 + 注入 4,857 + 复制带入 105 |
| `duplicate_rows` | **140** | 行 | 与注入的 140 条复制行一致 |
| `outlier_cells` | **70** | 单元格 | 每行只注入 1 个越界值 |
| `outlier_rows` | **70** | 行 | 行不重复计数 |
| `format_issue_cells` | **1,218** | 单元格 | 注入 1,198 + 复制带入 20 |
| `parse_error_cells` | **0** | 单元格 | 注入的格式问题都可解析 |

**两个容易被追问的差值**：

- 格式问题 1,218 比注入的 1,198 多 **20**：140 条复制行里有 20 个格式脏单元格被原样带入副本。
- 缺失 5,815 比“原生 853 + 注入 4,857”多 **105**：同理，复制行带入 105 个缺失格。

这不是计数错误。检测统计针对**当前这张表**，不是针对“原始来源行”。复制行在表里就是独立存在的行，它带的脏值应当被检测到。

### 4.4 不能相加

四类问题可以重叠（一个单元格可能同时是格式问题和异常值），所以**不能**把 `duplicate_rows + outlier_rows + format_issue_cells + parse_error_cells` 相加当成“有问题行数”。本表只给分项，不给合计。

`missing_by_column` 只统计**原始缺失**（实际空值 + `MISSING_TOKENS` 标记），不含解析失败产生的缺失——这是公共口径的硬性规定。

### 8.3 三个必答问题

**Q1：为什么要人工加入问题？**

真实数据已经存在缺失和重复（本项目参考数据就有 853 处原生缺失和 3 行原生重复），但这些问题的**种类、位置和规模**不受控，无法验证清洗流程对每一类问题是否真的生效。人工注入提供了一份“已知答案的考题”：我们知道注入了多少缺失、异常、格式问题，就能逐项比对检测器报出的数字。如果没有注入，检测出 5,815 个缺失也无法判断是漏检还是本来就有这么多。

注入只发生在训练集，测试集保持真实分布，因此清洗效果与最终评估不会被构造痕迹污染。

**Q2：参考数据是不是“完全干净的真值”？**

不是。参考数据是“人为加工前的底稿”，不是干净数据。实测结果：7,000 行里有 853 格原生缺失（集中在 `workclass`、`occupation`、`native_country`）以及 **3 行原生完全重复**；测试集 3,000 行有 431 格原生缺失。这些都不是我们造的，是原始 Adult 数据自带的。

因此“参考数据”的正确理解是**对照基线**：它告诉我们“不注入的情况下数据本身有多脏”，而不是“干净的标准答案”。这也解释了为什么测试集仍要做格式规范化和缺失填补——它只是不额外注入新问题。

**Q3：为什么要按来源组划分？**

Adult 数据里存在特征完全相同的记录（本项目 7,000 条训练参考中就有 3 组）。如果把完全相同或高度相似的记录拆到训练和测试两侧，测试集就等于在考“训练时见过的题”，指标虚高，这叫数据泄漏。

做法是把“14 个特征的规范化签名”作为分组键，同一签名下的所有记录只能落入一侧。配合两个措施：划分前计算签名（不是注入后），注入后保留原签名不重算。结果是训练 6,997 组、测试 3,000 组、交集为 0。

复制行同样受保护：它们保留来源行的 `_source_id` 和 `_group_id`，所以副本永远与来源在同一侧。
