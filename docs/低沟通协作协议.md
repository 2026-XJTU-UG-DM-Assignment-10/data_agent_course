# 低沟通协作协议 v2.0

本协议取代旧文档中需要全员同时在线的日常联调安排，业务契约仍为 v1.0。目标是固定接口、各自实现、通过文件异步交接，由一人集成；课程要求和真实证据要求保持不变。

## 1. 沟通安排

- 全体集中交流只保留一次开工确认和展示前排练。
- 第 4 天规则流程、第 6 天真实模型、第 8 天页面仍进行技术检查，默认由 D 异步执行，不要求全员在线。
- 不要求每天报进度；完成交付、发现真实阻塞或预计延期时更新交接文件。
- 普通技术选择由模块负责人自行解决。涉及公共契约的变化交 D 统一更新，其他独立工作继续。

## 2. 固定角色与归属

唯一机器可读清单是 `collaboration/roles.json`，包含每人分支、任务文件、允许修改路径、必须交付文件、函数签名、自测和离线输入。

- A 数据与检测；B 规范化与清洗；C 模型、计划、总流程与日志；D 分类、界面、公共文件与集成。
- 各人只主要修改自己的文件。扩充测试样例放入 `examples/role_X/`，不要改共享样例来让测试通过。
- `src/schema.py` 和 `src/contracts.py` 冻结，哈希见 `collaboration/contract_hashes.json`；不能改哈希绕过校验。
- D 正常开发也遵守冻结约定。确需公共接口升级时，记录变更、明确受影响角色、更新契约版本与说明，再统一发布；不要求无关成员停工开会。
- D 负责定位和合并，不代替所有人修复业务。每人的验证、文档、演示工作均计入实际贡献。

## 3. 不等上游的开发方法

| 成员 | 可立即使用的输入 | 依赖未完成时先做什么 |
| --- | --- | --- |
| A | 脏样本、已规范化样本、示例 QualityReport | 做正式数据构造和统计；自测可为缺失的 B 规范化依赖使用明确标记的测试替身 |
| B | 脏训练/测试样本、规则计划、清洗参考数据和状态 | 直接实现规范化及清洗，不等待 A 正式数据或 C API |
| C | 示例检测报告、合法/非法计划、模拟 LLMReply、示例 RunResult | 先做规则入口、计划验证、重试与日志；流程测试用受控依赖替身 |
| D | 干净训练/测试样本、示例指标、示例 RunResult 和示意矩阵 | 独立训练分类器，先完成页面展示；之后接 C 的真实总流程 |

所有样例均由 `examples/fixtures_manifest.json` 标记为非正式实验。示例指标不是真实分类结果，模拟模型返回不是真实调用。

替身规则：只替代其他成员尚缺失的依赖，不替代自己负责的核心功能；只放在自测或角色样例目录；正式代码不能静默退回替身。已有依赖实现报错时要暴露错误，不能伪装成“缺失依赖”切换替身。

每个自测支持 `--integration`，该参数要求使用真实的成员业务模块。模拟 LLM 客户端仍可用于明确标记的故障单测，但不能计作真实调用证据。

B 尽早交 `normalize_frame`，C 尽早交规则计划，作为部分可用的早期提交；不必等整个模块完成才上传。早期提交的状态仍为 working，不伪装成最终交付。

D 可以对这类小范围共享函数实际调用验证后提前合入 main，保持整份角色评审为 pending；这不代表整模块验收通过，也不替代之后的正式交付检查。其他成员仍可继续离线开发，不要求 D 立即上线。

## 4. 开发顺序

1. 阅读统一入口和对应角色指令，检查当前分支；保留已有修改，不自动重置、丢弃或整包覆盖。
2. 全员先运行 `python scripts/check_delivery.py --foundation`，确认共享文件可用。它不检查完整应用。
3. 在自己的分支实现 `roles.json` 要求的文件和 `checks/check_X.py`。角色自测必须真正调用本人的核心实现并验证有效行为。
4. 运行 `python checks/check_X.py`，把完整证据写到 `outputs/member_X/`，把少量脱敏摘要写到 `evidence/X/` 并随分支提交。正式数据来源/划分记录保存在任务书规定路径。
5. 按 [AI 使用记录规范](AI使用记录规范.md)更新本人的 `ai_usage/X/usage.json` 和实际脱敏提示词；再更新 `docs/handoff_X.md` 和 `handoffs/X.json`，只声明实际完成和实际验证的范围。
6. 执行 `python scripts/check_delivery.py --role X --submit`。通过后工具自动写 ready_for_review、检查时间、已测文件哈希和测试时的提交位置。
7. 查看 git diff/status，只提交本人文件，推送个人分支。交付不依赖额外的口头讲解。

`--submit` 会重新运行固定的本人自测，不执行交接 JSON 中随意填写的命令。它不是课程最终验收；通过后的文件如又修改，需重新检查。不要在最后检查之后再改 `docs/handoff_X.md`。

## 5. 交接结构与状态

每人维护两份对应文件：

- `docs/handoff_X.md`：简短说明完成内容、运行命令、真实结果、验证范围、已知问题和下一步。
- `handoffs/X.json`：机器可读状态、完成内容、验证项目、证据相对路径、阻塞及下一步。

成员状态只使用 `not_started → working → ready_for_review`；确实受阻时为 blocked。D 在 `docs/integration_log.md` 中另外记录 pending、accepted、changes_requested。退回后成员改回 working，修复并重新提交检查。

验证分成 fixtures、formal_data、real_llm、end_to_end，各自使用 not_run/passed/failed/blocked。通过项的 verification.evidence 必须引用本人 `evidence/X/*.json` 摘要，字段见 `evidence/README.md`；原始完整输出可不进 Git，不能用 `examples/` 输入文件冒充验证证据。

A 的正式模块交付要求 fixtures 和 formal_data 通过；B/C/D 的模块评审要求 fixtures 通过。C 真实调用未验证时可以先交离线可评审模块，但必须保留 real_llm=not_run/blocked，课程最终验收仍要求真实调用。

`ready_for_review` 表示声明范围已自测并可评审，不表示代码已合并或课程项目全部完成。自动检查不替代 D 对算法、证据和展示效果的实际判断。

成员 AI 完成本人交接后即可结束当前任务，不需要守候集成人或联系其他 AI。再次启动时先读评审记录，已接受且无新任务的部分不重复开发。

阻塞写成具体对象，例如：

```json
{
  "kind": "external_configuration",
  "reason": "真实模型凭据尚未提供",
  "needed_from": "模型配置负责人",
  "minimal_input": "在本地环境设置 LLM_API_URL/KEY/MODEL",
  "independent_work": "继续规则模式、日志和受控故障测试"
}
```

如果仍能交离线模块，把真实调用待配置记入对应验证项和下一步，而不是把整份离线模块的 blockers 留为未解决又要求通过 submit。只有真正阻止当前声明交付范围的事项才进入顶层 blockers。

## 6. D 的异步集成流程

1. 阅读成员交接和实际差异，按依赖顺序先 B，再 A、D，最后接 C 总流程；各模块开发仍可并行。
2. 对未合并的成员分支，成员先运行自己的交付检查；D 检查记录及文件差异后，以正常合并方式接入 main，禁止覆盖其他成员工作。
3. 正式数据尚未在集成人机器上准备时，先按 A 的命令 `python scripts/prepare_data.py --seed 42 --sample-size 10000` 重建。再在 main 运行 `python scripts/check_delivery.py --role X --integration`，复验提交状态、文件哈希、摘要及真实依赖自测；新输出写入 outputs，不重写成员提交的摘要。
4. 在 `docs/integration_log.md` 记录接受或退回。问题交对应负责人，附最小输入、复现命令、预期和实际结果，无需全员开会。
5. 四个模块齐备后，运行 `python scripts/check_integration.py --mode rules`。
6. 配好真实模型并取得实际调用证据后，运行 `python scripts/check_integration.py --mode llm`。
7. 合并四人的 AI 账本；C 从真实运行日志登记逐次模型请求，D 运行 `python scripts/summarize_ai_usage.py --check --require-records` 和不带参数的汇总命令。开发辅助与项目运行、实际费用与估算及不同币种分别列示，未知项明确保留。
8. 最后核对正式材料、换环境复现和全员排练。任一关键步骤未完成时保持待验证。

集成检查脚本只运行检查和写报告，不自动合并、切分支或推送。`scripts/smoke_check.py` 由 D 实现，必须支持 `--mode rules|llm --report PATH`，使用真实模块及正式数据，重新生成报告：

```json
{
  "status": "passed",
  "mode": "rules",
  "uses_real_modules": true,
  "formal_data_checked": true,
  "real_llm_checked": false,
  "evidence": ["outputs/实际运行ID/events.jsonl", "data/manifests/preparation_summary.json"]
}
```

以上仅为字段格式示例。LLM 模式的 real_llm_checked 必须为 true，并有实际请求与执行日志。不能复制示例作为成功证据。

## 7. 工具退出码与当前边界

| 命令结果 | 含义 |
| --- | --- |
| 0 | 该命令声明范围检查通过 |
| 1 | 检查失败、异常或冻结契约不一致 |
| 2 | 尚未交齐、角色/分支不符、缺少证据或未达当前交付标准 |

业务代码尚未实现时，角色交付或集成检查返回 2 是正确结果。不得为获得绿色结果而补空函数、空自测或伪造 JSON。

## 8. 最少需要沟通的情况

仅在缺失角色、外部凭据/权限/原始文件确实不可得、公共契约存在冲突、交付预计延期时，发一次具体说明。普通实现和自测问题先在本人模块解决，其余工作继续。不得因等待一句口头确认而停止全部工作。
