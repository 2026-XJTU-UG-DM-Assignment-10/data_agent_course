## 2. 项目目标与边界

项目名称：**基于大模型的数据自动清洗与分类智能体**。

最小目标：针对一个固定结构的表格数据集，自动完成“质量检测 → 模型制定处理计划 → 工具执行 → 结果复查 → 分类评估 → 文件导出”，并保留运行记录。

### 必须完成

- 处理的数据至少 5,000 条记录、10 个字段；本项目计划使用 10,000 条参考记录和 14 个特征。
- 覆盖缺失值、重复数据、异常值或噪声、类型或格式不一致四类问题。
- 至少一个真实大模型根据检测摘要选择处理策略，随后由代码自动执行。
- 支持一个二分类任务，只使用逻辑回归。
- 一个可以演示的 Streamlit 页面，以及一个命令行运行入口。
- 输出处理前后统计、分类结果、处理后的数据、运行日志。
- 提供老师要求的六类交付物，见第 10 节。

### 本次不做

- 多智能体、聚类、自动机器学习、复杂特征工程、模型搜索。
- 多数据集、多分类器、多组随机种子对照、统计显著性检验。
- 跨表匹配、标签修复、字段冲突消解、复杂异常检测。
- 账号、数据库、远程部署、任务队列、前后端分离。
- 任意 CSV 的通用理解。只支持本文规定的 Adult 字段结构。

## 3. 数据与分类任务

### 数据来源

使用 UCI Adult 数据集。官方说明包含 48,842 条记录和 14 个特征，目标为预测年收入是否超过 50,000 美元，且存在原生缺失值。

官方页面：<https://archive.ics.uci.edu/dataset/2/adult>

为减少处理步骤，优先从官方下载包中的 `adult.data` 构建演示样本，不必合并 `adult.test`。在 README 和报告中注明来源及 CC BY 4.0 许可，保留原始文件。

### 固定字段

统一使用以下 14 个特征，另加标签 `income`：

```text
age, workclass, fnlwgt, education, education_num,
marital_status, occupation, relationship, race, sex,
capital_gain, capital_loss, hours_per_week, native_country
```

数值字段为 `age、fnlwgt、education_num、capital_gain、capital_loss、hours_per_week`；其余为类别字段。

标签统一为 `<=50K` 和 `>50K`。只做标签外围空格、末尾句点等确定性格式规范化，不修改或注入错误标签，不把标签或辅助 ID 当成特征。

### 数据构造顺序

1. 下载或读取真实原始文件。网络不可用时，提供手动放入文件的路径说明，不生成冒充 Adult 的替代数据。
2. 按官方字段解析，保留原始文件；为记录生成稳定的来源 ID，仅用于追踪和分组。
3. 进行必要的确定性格式解析，排除没有合法标签的记录并记录数量，建立参考数据池。参考数据仍可能存在原生缺失，不能称为“完全干净的真值”。
4. 固定随机种子 `42`，抽取 10,000 条参考记录。
5. 按规范化后的 14 个特征签名分组，使用分组随机划分得到约 70% 训练集和 30% 测试集，保证同一组不跨集合。训练集需超过 5,000 条。
6. 只在训练集内注入下表规定的问题，生成 `train_dirty.csv`；测试集保存为 `test_reference.csv`，不额外注入问题。
7. 保存抽样、划分、注入参数和注入记录。测试集一旦确定，开发期间不根据它调整清洗策略或模型参数。

### 四类质量问题

| 类型 | 构造规则 | 最小处理办法 |
| --- | --- | --- |
| 缺失值 | 保留原生缺失；在训练集约 5% 的非缺失特征单元格中注入缺失 | 数值均值/中位数填补；类别众数/Unknown 填补 |
| 重复数据 | 复制约 2% 的训练记录，保留来源关联 | 按 14 个特征和标签识别完全重复记录，训练时保留一条 |
| 异常值 | 在约 1% 的训练记录中，将年龄改成 -5/999，或周工时改成 0/999 | 按明确范围识别，置为缺失，再填补 |
| 类型或格式不一致 | 在约 3% 的非缺失数值特征单元格中加入空格或 ` hours`、` years` 等单位后缀 | 按字段解析并统一为数值，记录转换数量 |

比例为默认构造参数，不是验收指标。新增单元格问题尽量不重叠，复制重复行放在其他问题注入之后，避免彼此覆盖。不要修改 `income` 和来源 ID。

`injection_manifest.csv` 至少记录来源 ID、字段、问题类型、修改前值和修改后值。它仅用于构造审计和离线检查，不提供给模型，也不参与填补或分类。

## 4. 最小技术方案与接口

使用 Python、pandas、numpy、scikit-learn、Pydantic、requests、Streamlit。依赖中记录实际验证过的版本。只接入一种用户可用的模型服务，通过独立适配器封装 HTTP 调用，接口协议按所选服务的官方文档实现。

不要求使用 LangChain 或其他智能体框架。采用“模型制定计划、Python 执行、执行后复查”的工作流即可。

### 主流程

```text
训练 CSV → 质量检测 → 模型生成 JSON 计划 → 校验计划
    → 格式规范化 → 训练集去重 → 非法值置空
    → 从训练集学习填补值 → 填补训练集并复查
    → 使用相同规则和训练集填补值转换测试集
    → 训练逻辑回归 → 测试集评估 → 导出全部结果
```

质量检测必须能够发现“格式转换后才暴露的异常”，例如 `999 hours`。可在检测时使用不修改原文件的解析视图。

### 关键接口

以下是统一后的 v1.0 接口。完整参数类型、统计口径和文件归属见公共接口说明；公共类直接从共享的 `src/schema.py` 导入，不要在各模块重新定义。

```python
normalize_frame(df) -> (normalized_df, NormalizationAudit)
profile_data(df, *, dataset="train", stage="before") -> QualityReport
get_cleaning_plan(train_report, *, mode, llm_client=None, event_sink=None) -> CleaningPlan
clean_training_data(train_df, plan) -> (clean_df, cleaning_state, audit)
transform_test_data(test_df, cleaning_state) -> (clean_test_df, audit)
train_and_evaluate(clean_train, clean_test, *, output_dir, seed=42) -> ClassificationResult
run_pipeline(train_path, test_path, *, mode, output_dir="outputs", seed=42,
             llm_client=None) -> RunResult
```

- `QualityReport`：样本数、字段类型、缺失统计、重复统计、非法值统计、格式问题统计。
- `CleaningPlan`：填补方法、固定处理步骤、选择理由、模式。
- `cleaning_state`：训练集学得的填补值、类别处理规则和字段信息，可序列化。
- `audit`：各步骤修改数量、删除数量、处理前后统计、警告和错误。
- `RunResult`：状态、模式、指标和输出文件路径，不返回 API 密钥。

`normalize_frame` 由 B 维护，A 的检测与 B 的清洗共用；`run_pipeline` 由 C 维护，D 的页面和 CLI 只调用此接口。模型分类结果返回一个 `ClassificationResult`，不返回模型与指标元组。

### 格式与异常处理规则

- 将 `?`、空字符串、实际空值和公共常量规定的其他缺失标记统一识别为缺失；类别只去外围空格，保留原有大小写，固定填充值为 `Unknown`。
- 数字只剥离预先允许的字段单位后缀，转换失败时记录错误并按缺失处理。
- 年龄有效范围为 17–120；每周工时为 1–168；教育年级编码为 1–16；资本收益和损失非负；`fnlwgt` 大于 0。
- 只处理明确违反上述规则的数值。合法的高收入相关数值不因偏大就自动删除。
- 训练集只允许因完全重复而删除记录；测试集不去重、不删除记录、不改变标签。
- 填补值、标准化参数、类别编码器均只在训练集拟合，再用于测试集。
- 填补后可能出现新的完全重复，训练集最终再复查去重；两轮删除数量分别记录。
- 数据附加 `_source_id、_group_id` 两个审计字段，始终排除在 14 个建模特征之外。注入后不重算来源组，训练/测试不交叉。

数据边界参考：<https://scikit-learn.org/stable/common_pitfalls.html#data-leakage>

## 5. 智能体的最低实现要求

### 模型读取什么

只传入训练集的字段说明、问题数量、缺失比例、数值分布摘要，以及必要的少量样例。不要传入完整数据、测试集统计、测试指标、问题注入真值或凭据。

### 模型决定什么

至少根据摘要选择数值与类别填补策略，并说明依据。例如数值明显偏斜时选中位数，类别缺失较多时选 Unknown。允许的策略只有：

- 数值：`mean` 或 `median`。
- 类别：`most_frequent` 或 `constant`；常量固定为 `Unknown`。

四类基础处理步骤必须执行，模型不决定是否跳过作业要求。模型输出按 Pydantic 白名单校验，不执行模型生成的任意代码。

示例计划仅用于解释结构，不是可直接冒充真实模型结果的运行记录：

```json
{
  "contract_version": "1.0",
  "mode": "llm",
  "steps": [
    "normalize_format",
    "drop_duplicates",
    "mark_invalid",
    "impute_missing"
  ],
  "numeric_imputation": "median",
  "categorical_imputation": "constant",
  "categorical_fill_value": "Unknown",
  "reason_numeric": "根据训练摘要中的偏斜分布选择中位数。",
  "reason_categorical": "使用独立类别保留缺失信息。"
}
```

### 两种运行模式

- `llm`：真实模型生成计划，是课程智能体演示的主要模式。
- `rules`：固定选择中位数和 Unknown，用于本地开发及故障备用；页面、日志和报告必须显示“规则模式”。

每次运行最多请求模型两次，总预算包含重试。响应超时默认 30 秒。第一次出现返回格式错误时，把校验错误反馈给模型进行一次修正；第二次仍失败则明确停止，保留失败日志，允许用户另行选择规则模式。不要静默降级并宣称真实智能体运行成功。

环境配置示例：

```text
LLM_API_URL=
LLM_API_KEY=
LLM_MODEL=
LLM_TIMEOUT_SECONDS=30
LLM_MAX_CALLS=2
```

API 调用细节集中在 `LLMClient` 适配器，业务流程不依赖供应商名称。缺少实际凭据时，`.env.example` 和清晰的配置说明必须完成，但验收报告应把真实调用列为“待验证”。

### 必须保存的运行记录

使用 `events.jsonl` 或同等简单结构保存：

- 运行 ID、时间、模式和软件版本。
- 实际供应商、模型标识、调用参数、提示词、原始返回与解析后的计划。
- 工具名称、参数、执行状态、耗时和修改数量。
- 失败原因、校验错误、重试过程、最终状态。
- 调用次数；服务返回的 token 使用量；可核实的成本及计价依据。

未知 token 或价格记为 `null`/“未知”；不能用 0 冒充实际免费。不得记录密钥或含凭据的请求头。

## 6. 分类、页面与输出

### 分类

只使用 `LogisticRegression`。数值字段标准化，类别字段独热编码并允许测试阶段出现未知类别，统一由训练集拟合。

固定随机种子；使用足够的迭代上限，遇到收敛警告时作合理调整。输出 Accuracy、Macro-F1、混淆矩阵和各类别样本数。报告说明 Macro-F1 的含义，不只写不明确的“F1”。

不要求与其他模型比较，不要求比清洗前提高多少分。不得编造提升比例。主要证据是处理前后质量统计，以及一个有效的分类结果。

### 一个 Streamlit 页面

至少包含：

1. “使用演示数据”入口，自动选择准备好的训练集和测试集。
2. `llm` / `rules` 模式选择，当前模式始终可见。
3. “开始处理”按钮。
4. 处理前后四类问题统计和实际删除/修改数量。
5. 模型选择的策略与理由。
6. Accuracy、Macro-F1、混淆矩阵。
7. 处理后 CSV、结果摘要和日志的下载入口。
8. 当前步骤、错误和明确的成功/失败状态。

时间允许时增加同字段结构的训练/测试 CSV 上传；它不是第一版必须项。Streamlit 页面重绘或点击下载不能自动重复请求模型；明确点击开始才创建新运行。

### 每次运行的输出

```text
outputs/<run_id>/

  quality_after.json
  cleaning_plan.json
  cleaning_state.json
  train_processed.csv
  test_processed.csv
  metrics.json
  confusion_matrix.png
  summary.md
  events.jsonl
  audit_train.json
  audit_test.json
  run_result.json
```

输出人可读的处理后数据，保留 14 个特征和标签。来源 ID 如保留需单独注明，不进入模型。无需额外实现模型服务或部署。

| 第 1 天 | 数据来源、字段、接口、配置与分工确定 |
| 第 2–4 天 | 检测、清洗、分类在规则模式中完整跑通 |
| 第 5–6 天 | 接入真实模型；计划、工具执行和日志联通 |
| 第 7–8 天 | 页面联通；完成一次真实成功运行；检查边界和错误处理 |
| 第 9 天 | 完成报告、PPT、演示稿、贡献说明和验收记录 |
| 第 10 天 | 按 README 重新复现；全组排练；修复阻断问题 |
| 剩余时间 | 演示备份、答辩准备和必要修复 |

开发优先顺序为：数据与本地闭环 → 真实模型 → 日志与界面 → 展示材料。不要在核心流程未跑通前美化页面。

## 9. 最低验收与验证方式

请填写 `docs/acceptance.md`，逐项写“通过 / 未通过 / 待验证”，并提供真实输出路径或命令结果。

| 验收项 | 通过标准 |
| --- | --- |
| 数据规模 | 注入前后训练数据及处理后训练数据均不少于 5,000 条，保留至少 10 个特征字段；实际计划为 14 个 |
| 四类问题 | 演示训练集中确实存在四类问题，检测摘要可见，处理数量有记录 |
| 处理有效 | 明确非法值得到处理；填补后无未处理缺失；训练集无完全重复；数值字段可用于模型 |
| 真实智能体 | 有实际模型返回的策略、理由和工具执行记录；规则模式不能替代此项 |
| 分类 | 逻辑回归能训练、预测；Accuracy、Macro-F1 和混淆矩阵来自真实测试 |
| 无数据泄漏 | 来源组不跨训练和测试；所有学得参数仅使用训练集；来源 ID 和标签不进入特征 |
| 可追踪 | 原始数据未覆盖；构造参数和注入记录存在；清洗修改与错误可追踪 |
| 页面 | 能运行演示、查看结果、下载数据及日志；当前模式可见 |
| 可复现 | 新终端按 README 能完成规则模式运行；配置凭据后能执行真实模型模式 |
| 材料完整 | 第 10 节六类交付物齐全，正式文件可打开 |

`smoke_check.py` 重点验证有意义的完整行为即可，不需要复杂测试框架：

- 规则模式完整执行后，四类问题确实被处理，输出数据规模仍达标。
- 原始文件未变更，训练/测试来源组不重叠，测试集行数和标签未改变。
- 错误模型 JSON 被明确拒绝，失败记录存在，不伪造成功。
- 模型缺失凭据时给出明确状态，规则模式仍可使用。

至少保留一份真实模型成功日志，以及一份明确标记的受控故障测试记录。故障测试可用构造的错误响应验证解析和修正逻辑，必须标注为测试，不声称是自然发生的模型错误。

不设置准确率、F1、检测准确率或性能提升门槛；结果正常、可解释、可复现即可。真实模型未配置或未跑通时，必须把该验收项列为待验证，不能宣称整体全部通过。

## 10. 六类正式交付物

### 1. 报告

保留 `docs/report.md` 源文件，导出 `docs/report.pdf`。目标 5–6 页，最多 10 页；以实际导出的页数为准。

建议内容：任务与目标、数据来源及问题构造、智能体流程、实现方式、真实结果、局限和分工。引用官方数据来源。用实测结果填写表格，尚未测量处清楚标注，不生成虚构数字。

### 2. 源代码

提供完整源码、README、依赖文件、配置示例、数据准备和运行命令。提供一份可直接交给组员运行的项目目录或压缩包，排除密钥、虚拟环境和缓存。

### 3. 数据

交付原始文件、抽样参考数据、训练/测试划分、问题训练数据、处理后数据，以及构造脚本和注入记录。若不能随包提供原始数据，必须给出真实来源和完整获取、构造步骤。

### 4. 展示 PPT

提供 6–7 页可打开的 `docs/presentation.pptx`，并保留文字提纲。总汇报 7 分钟，另备 3 分钟问答。

- 背景与要求：1 分钟。
- 数据和智能体流程：1 分钟。
- 现场演示：2 分钟。
- 质量统计和分类结果：2 分钟。
- 总结与分工：1 分钟。

PPT 使用真实页面截图和实际结果。能使用文档或幻灯片工具时完成正式导出并检查排版；如果环境确实无法导出，应完成所有内容并明确指出缺失的正式文件，不把提纲当作已生成 PPT。

### 5. 个人贡献说明

`docs/contributions.md`：四位成员姓名由实际组员填写，记录负责模块、实际代码/文档工作、演示职责。未知信息留“待填写”，不编造贡献比例。

### 6. 智能体运行记录

交付至少一份完整真实成功运行目录，包含提示词、模型与参数、工具调用、处理结果、调用次数和可核实的成本；同时保留错误与修正测试记录。

## 11. 演示与答辩准备

演示固定使用预先准备好的数据，按“问题统计 → 模型计划 → 处理结果 → 分类结果 → 下载日志”的顺序进行。现场正常运行用真实模型模式。

另存一份成功运行结果和简短录屏，用于网络或服务故障时回放；回放时明确说明是之前的真实运行记录。只在用户明确选择时使用规则模式，并说明当前模式。

准备以下问题的简短回答：

1. 智能体自主决定了什么？答：依据检测摘要选择填补策略，给出理由，再自动执行受控工具并复查。
2. 为什么人工注入问题？答：保证覆盖四类要求，让构造过程可复现；原生问题与注入问题分开说明。
3. 为什么选这些清洗方法？答：方法简单、容易解释，适合本数据的字段类型和明确非法值。
4. 如何避免测试信息泄漏？答：先分组划分，模型只看训练摘要，所有学得参数只来自训练集。
5. 系统有什么局限？答：仅支持固定字段，异常规则有限，未研究复杂冲突或多模型性能比较。

## 12. AI 完成工作后的汇报格式

最终只需给出：

1. 已完成的功能，以及实际通过的验收项。
2. 实际验证过的启动、数据准备和运行命令。
3. 一次真实运行的数据规模、质量变化、Accuracy、Macro-F1 和日志路径；没有真实模型调用时明确说明。
4. 正式报告、PPT、数据包和项目目录的位置。
5. 尚需组员完成的事项，例如配置模型凭据、填写姓名、确认展示课次；以及任何尚未生成或未验证的正式文件。

不承诺成绩，不宣称尚未实际完成的功能。完成上述范围后停止加功能，优先保障展示稳定。
